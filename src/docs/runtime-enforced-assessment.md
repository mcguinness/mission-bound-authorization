# Runtime-Enforced reference assessment

A claim-to-evidence assessment of the reference runtime composition: the
`mcp-payments` Policy Enforcement Point (PEP), the reference Policy Decision
Point (PDP), OpenFGA and the Mission kernel, as `composeStack`
(`src/demo/src/stack.ts`) assembles them. Every statement below is true of
the reference implementation at commit `a90a25c8`, the origin/main commit
read. The tree read was `a90a25c8` plus this branch's two commits, which
change only `draft-mcguinness-mission-runtime.md` and
`src/docs/CONFORMANCE.md`. Before it merged, origin/main moved to
`8b60e394`; those commits change no implementation file, configuration,
or runtime ledger row identifier.

Every behavioral statement cites the function (file and symbol) or the exact
test (`file > describe > it`) that shows it. A path with no witnessing test
says "no test yet". The tests were not run for this document (no installed
dependencies; many witnesses need a live OpenFGA). Each cited test path was
matched against its file with the ledger validator's own matcher
(`matchingDeclarations`, `scripts/test-title-paths.mjs`). Only the three
`src/demo/test/` files `remote-pdp-stack`, `mas-join-stack` and
`pep-emission-boundary` run `composeStack` itself; the other witnesses
exercise `Pep`, `McpPaymentsServer`, `evaluate` or `createDecisionChannel`
with fixture dependencies.

## 1. Scope and claims

This is an implementation-coverage record for one composition at one
commit, and the evidence base that #253's deployment contract is to link
(§9). It keeps four things separate:

- **Specification completeness**, whether the drafts say enough: not assessed.
- **Implementation coverage**, which requirements the reference implements
  and tests: the only thing assessed. Ledger statuses (§6) are coverage
  states, not percentages of production correctness, and the ledger is not a
  complete inventory of the drafts' requirements.
- **Operational validation**, behavior under load, failure, restart and real
  networks: none beyond the cited tests; §7 lists the gaps.
- **Independent interoperability**: one implementation exists, so nothing
  here is interoperability evidence.

Passing the manifest validators shows mechanical consistency only (quoted
clauses present, cited tests declared and collected). It does not show that
a claim holds.

What the composition asserts:

- It publishes an Enforcement Scope Statement (§3) that declares a mediated
  scope. The statement has no `claims` member, so it claims no named
  extension (`EnforcementScopeStatement.claims`,
  `src/services/pdp/src/enforcement-scope.ts`).
- It states no assurance level and no maturity. Maturity is published only
  in `DRAFTS.md`.

Spec revisions the cited rows were validated against
(`conformance-manifest.json` `source.specs`): Runtime `79344a58`, AuthZEN
profile `48b7abcd`, Runtime Evidence `48b7abcd`, and Authority Server
`7a1fdb45` for the join route in §4.

## 2. Topology and trust assumptions

**One process, one writer.** `composeStack` assembles every component in the
calling process (`src/docs/control-plane-deployment.md`).

| Component | Placement | Source |
|---|---|---|
| Mission state | In-process `MissionKernel`, issuer `https://as.demo` (`config/topology.json` `issuers.as`). With `withAuthServer`, the reference AS at `http://localhost:{asPort}` (default 4400) owns the kernel and signs the tokens | `composeStack` |
| Resource and PEP | `McpPaymentsServer` and `Pep`, in-process. The audience `http://localhost:4403/mcp` (`resources.payments`) is an identifier: nothing listens on 4403. HTTP MCP channels bind ephemeral `127.0.0.1` ports | `createHttpMcpChannel` (`src/services/mcp-payments/src/mcp-http-transport.ts`) |
| PDP | `createDecisionPoint`. Co-resident by default (a direct call); `MISSION_PDP_MODE=remote` puts it behind a loopback HTTP listener on an ephemeral `127.0.0.1` port | `createDecisionChannel` (`src/services/pdp/src/decision-channel.ts`), `createPdpHttpServer` (`server.ts`) |
| Resource policy | OpenFGA at `openfga.url` (`https://localhost:8080`), the one external dependency. `composeStack` connects before anything else | `Fga.connect` (`src/services/pdp/src/fga.ts`) |
| Approval | `AccessRequestService`, in-process; issues ARAP approval state audienced to `https://pdp.demo` | `composeStack` |

**Token validation.** Without the AS, the resource gets an empty JWKS and
the tests drive the PEP with token facts. With the AS, the resource verifies
against the AS JWKS fetched once at assembly (`serverJwks`, `stack.ts`;
`createLocalJWKSet` in `McpPaymentsServer`). Over HTTP, a DPoP proof is
required before the PEP runs:
`src/services/mcp-payments/test/mcp-http-channel.test.ts > HTTP mediated MCP channel (harness duty 2 + DPoP proof-of-possession over HTTP) > 4a: DISCRIMINATING token-without-a-DPoP-proof (valid token, no proof header; and the bearer scheme) is rejected at the gate BEFORE the PEP -- zero evidence/ledger; a valid DPoP client on the SAME server then permits`.

**State source.** The PDP's only trusted source is `loadView`, a synchronous
read of the in-process kernel stamped `observed_at` at read time, source
`load_view` (`ALLOWED_FRESHNESS_SOURCES`, `stack.ts`). In the composed stack
each observation is taken during the request it serves, so the declared
bounds (300 s ceiling; 30 s, 60 s and 300 s per class, §3) are never
approached. Staleness handling is shown only with injected observations:

- `src/services/pdp/test/permit-deadline.test.ts > permit deadline (@spec runtime#state-freshness) > caps a bounded class at the accepted observation plus the class bound, not at the permit lifetime`
- `src/services/pdp/test/evaluate.test.ts > PDP decisions against OpenFGA (@spec authzen) > stale freshness beyond the bound -> deny stale_state`
- `src/services/pdp/test/evaluate-fail-closed.test.ts > evaluateInner fail-closed gaps (#608) > GAP 3: malformed/future/untrusted freshness fails closed, never merely shape-checked (@spec runtime#state-freshness) > a well-formed, fresh observation from a source outside the deployment's allowed set denies stale_state, for every high-consequence class`

**Clock.** One clock is assumed. The PDP tolerates 5 s of future skew on
`observed_at` (`DEFAULT_FRESHNESS_SKEW_TOLERANCE_SECONDS`, `evaluate.ts`):
`src/services/pdp/test/evaluate-fail-closed.test.ts > evaluateInner fail-closed gaps (#608) > GAP 3: malformed/future/untrusted freshness fails closed, never merely shape-checked (@spec runtime#state-freshness) > a future observed_at within the skew tolerance still permits (boundary control: the tolerance itself is not itself a denial)`.

**Remote decision channel** (remote mode only). A per-PEP HMAC secret,
generated at each `createDecisionChannel` call, MACs the request and the
response under separate domains (`channel-mac.ts`). The response MAC binds the
request. The PDP admits only a registered PEP for its declared audience and
refuses a nonce reused inside a 30 s window, before any evaluation
(`createPdpHttpServer`). Each call's deadline is capped by the action class's
window (`channelDeadlineMs`). Tests:

- `src/services/pdp/test/remote-channel.test.ts > Remote Decision Channel (@spec runtime#decision-channel) > a validly signed request over a real HTTP hop permits, and the PEP verifies the response signature`
- `src/services/pdp/test/remote-channel.test.ts > Remote Decision Channel (@spec runtime#decision-channel) > a PEP submitting a decision request outside its authorized enforcement scope is refused before evaluation, with zero PDP evaluation`
- `src/services/pdp/test/remote-channel.test.ts > Remote Decision Channel (@spec runtime#decision-channel) > a replayed request (same nonce) is refused the second time, with the PDP evaluated only once`
- `src/demo/test/remote-pdp-stack.test.ts > demo configured remote PDP route > wires a real decision hop behind the flag and fails closed when that PDP stops`

**Keys and stores.** Every signing key `composeStack` uses is generated at
boot under its configured `kid` (`config/topology.json` `keys`), including
the PDP's Decision Evidence key (`pdp-decision-evidence`). Every runtime store
opens in memory: `openStore` defaults to `:memory:`
(`src/packages/store/src`), and `TransactionEngine`, `Connectors`,
`PaymentsStore` and `EvidenceRetentionStore` are built without a file.

**Finding A: declared classes are not all instantiated.** The PEP's
Operation Profile (`TOOL_ACTIONS`, `src/services/mcp-payments/src/pep.ts`)
assigns `irreversible_action` to `execute_wire_transfer` and
`external_commitment` to `send_remittance_email`. The other six tools,
`schedule_payment` and the `check_transfer`/`hold_transfer` phases included,
reach the PDP with no `action_class`. The PDP then applies the
`consequential_read` posture (`postureStalenessBound`, `runtime-posture.ts`),
and Decision Evidence records `consequential_read`
(`createDecisionEvidenceEmitter`, `decision-evidence.ts`). No operation is
labeled `consequential_write`, though `src/docs/operation-profile-payments-v1.md`
classifies `schedule_payment` as consequential and reversible. Unlabeled
requests are not refused for missing freshness:
`src/services/pdp/test/evaluate-fail-closed.test.ts > evaluateInner fail-closed gaps (#608) > GAP 2: freshness absence fails closed for high-consequence classes (@spec runtime#state-freshness) > no action_class at all, context.freshness absent -> permit (unclassified requests are unaffected)`.

**Finding B: an undeclared establishment mode.** Because
`config/mas-join.json` lists the payments resource in `governed_resources`,
`composeStack` also starts a MAS-governed channel. Its tool calls are
mediated by the same PEP on the declared execution path, but it establishes
the Mission from a `Mission-Reference` field on an ordinary credential
(baseline Join, Authority Server companion), not from a token claim. The
statement's `mission_establishment_mode` names only `token-claim`:

- `src/demo/test/mas-join-stack.test.ts > composed stack: the MAS-governed channel joins an ordinary credential (#557) > starts the MAS-governed channel because config/mas-join.json names this resource governed`
- `src/demo/test/mas-join-stack.test.ts > composed stack: the MAS-governed channel joins an ordinary credential (#557) > permits a joined read end to end, with authority drawn from the referenced Mission`

## 7. Exclusions

What this composition does not cover:

- **Topology.** One process and one writer. Multi-process serialization and
  claiming stay under #641's trigger (`src/docs/control-plane-deployment.md`).
  The "two replicas" transaction tests share one consumption store in one
  process:
  `src/services/mcp-payments/test/transaction.test.ts > M5 transaction-assurance tier > executes once across two replicas sharing a consumption domain, whatever token jti carries the txn`.
- **Restart recovery.** Every runtime store is in memory and every key is
  regenerated at boot (§2), so permits, redemptions, pending operations and
  retained evidence do not survive a restart. Retention recovery is shown
  only on a file-backed store in a unit test, which the stack does not use:
  `src/services/mcp-payments/test/decision-evidence-retention.test.ts > retention honors the declared audit window (@spec runtime-evidence#receipt-retention) > recovers the retained records, the emitter sequences and the key retirement metadata after a restart`.
  On the control-plane side the continuation and delegation-family
  projections restart empty and no restart-recovery claim is made for them
  (`src/docs/control-plane-deployment.md`). A runtime restart test: no test
  yet.
- **Delivery and atomicity.** External delivery is at least once with
  idempotent acceptance, never exactly once; the provider access-token count
  is not coupled to token acceptance (`src/docs/control-plane-deployment.md`).
- **Action classes.** `consequential_read` and `consequential_write` are
  declared but carried by no request (§3 finding A).
  `privileged_administration`, `non_consequential` and `audit_only` have
  postures but no operation.
- **Establishment modes.** The statement declares `token-claim` only; the
  MAS-governed route's join establishment is undeclared (§3 finding B).
- **Named claims and optional modes.** No named extension is claimed (§5).
  Only the `deny` unavailability posture, no replication and no break glass
  load; anything else is refused (`loadRuntimePosture`). No permit reuse or
  outage ride-through exists.
- **Idempotency domain.** The PDP holds none; the PEP's store is single
  process (the blocked `runtime.idempotency.*` rows, §6).
- **Resources.** `Connectors` is an in-memory stub
  (`src/services/mcp-payments/src/connectors.ts`) with no declared
  conditional-effect, outcome-lookup or cancellation capability (#817).
- **Remote channel.** A reference adapter: no TLS, an in-memory nonce store,
  a per-assembly shared secret (`src/services/pdp/src/server.ts` header).
- **Operational validation.** No load, partition, clock-fault or long-run
  testing. Freshness bounds are shown only with injected observations (§2).
- **Interoperability.** One implementation. No second PEP, PDP or AS has
  run these paths.
- **Other surfaces.** The issuance floor is covered separately
  (`src/docs/issuance-only-deployment.md`). The agent harness, egress gate,
  RAS and cross-domain paths that `composeStack` also builds are outside this
  assessment.

## 8. Unresolved seams

- **#250, "Family: control-plane consistency and availability architecture"
  (open).** The reference meets the Control Plane invariants only in part:
  `expected_version` is not parsed, projections restart empty, and nothing
  detects a restore from an older backup. A runtime that reads kernel state
  inherits those limits.
- **#831, "Credential operations: provide durable signing identities, key
  rotation and verifier refresh" (open).** Keys are generated per boot under
  fixed `kid`s and verifiers hold boot-time JWKS snapshots, so neither
  restart continuity nor rotation of token, challenge or evidence keys
  can be shown.
- **#817, "Runtime adapters: declare and enforce resource-side execution
  capabilities" (open).** Parameter digests, single-use permits and leases do
  not prove that the resource stayed unchanged or that a timed-out effect did
  not commit. No connector declares conditional effects, outcome lookup,
  commit point or cancellation, so transaction-grade claims have no resource
  witness.
- **#594, "Ledger: missing tests and the per-requirement profiles field"
  (open).** It tracks the floor's missing tests, which are most of the `todo`
  rows in §6; it excludes #773's rows (the `runtime.evaluation-context-binding`
  rows), and the `runtime.operational.*` rows belong to #310. Its W4-3 and
  W4-4 slices are blocked on #786, and the shipped Evidence claim stays off
  until W4-16 has audited its duties.

# Mission Resource Access supported-subset fixture

This directory freezes the initial interoperable implementation subset of `mission_resource_access` (#819) against a concrete resource contract (#249, D553, D676). It is an implementation profile for consumers that implement less than the whole type, not a requirement on every conforming implementation. A consumer that runs the cases under it produces evidence for that consumer only. The reference implementation running them is not independent interoperability (D414).

Every file is frozen. A changed contract is a new contract version with its own digest, and a changed subset is a new subset file with its own `id`; no file is edited in place. The reference implementation's tests compare the newest pair with the contract the payments resource declares as current and with the sets its engine supports, and check that the superseded `2026-10-20`, `2026-10-24` and `2026-10-26` versions stay declared as they were frozen (`src/services/authorization-server/test/resource-access-subset.test.ts`). The second consumer below runs under `supported-subset.json`, whose capabilities the newer subset keeps unchanged.

## The contract

`reference.digest` is `sha-256:` followed by the unpadded base64url SHA-256 of the JCS (RFC 8785) serialization of `document`, so a consumer can recompute it without this repository. The document assembles, for each operation, its action identifier and phase, action class, operation-target rule, parameter form, idempotency key and catalog capability, and it names the fact the resource reads for each constraint key (Resource Access, Resource Contracts; the payments Operation Profile `payments-runtime-profile-v13` it names). Resource policy, Mission state, entitlements, revocation and resolved resource facts are not contract material.

## Applicability

Resource Contracts has the authorization server read, from trusted resource or deployment configuration, which contract version is current for an entry's `resource`, and refuse a proposed `resource_contract` that is not the reference of a contract that configuration names as current for that resource. `payments-contract-applicability-v16.json` is that configuration for this fixture: the payments contract's version `2026-10-27` is current for `https://payments.example/mcp`, matched exactly, and is current for no other resource. `payments-contract-applicability-v15.json`, frozen before `payments-runtime-profile-v16`, under which version `2026-10-26` was current, and `payments-contract-applicability-2026-10-26.json`, frozen before `payments-runtime-profile-v15`, under which version `2026-10-24` was current for the same resource, are the historical configurations; each is kept, unedited, with its cases. Each file states currency only. Whether a resource requires a reference, and the versions' states and retention, are outside it: the reference deployment requires none (`requires_reference` is empty), and turning the requirement on for payments is a separate migration (#249, D865).

Each file's `entry-validation` cases carry its configuration inline as `contracts`, so the case files stay consumable on their own: the current reference is admitted on the payments resource and refused on an unrelated one, a version the configuration does not name as current is refused, and a reference with no configuration is refused. Cases ev-rc-09 to ev-rc-12 do so for the current file, naming `2026-10-26` as the version not current; ev-rc-05 to ev-rc-08 do so for the v15 file and ev-rc-01 to ev-rc-04 for the oldest one, both historical. The reference implementation's tests check that each file's cases carry exactly its configuration and that every case carrying a configuration carries one of the three; that the current file's reference is the version the payments deployment declares current (`2026-10-27`); and that each historical file's reference is a version the deployment still declares and performs (`2026-10-26` and `2026-10-24`, each superseded within its retention). The frozen contract and subset files are unchanged.

## The subset

| Member | Meaning |
|---|---|
| `contract` | The frozen contract the subset is defined against: its file and its reference |
| `resource_match` | The matching modes in the subset: `exact` only (an absent `resource_match` is `exact`) |
| `actions` | The explicit action identifiers the subset uses: the contract's own, and no action family |
| `members` | The entry members a subset consumer implements |
| `constraints` | The constraint keys a subset consumer implements, each with the specification that registers it in the Mission Common Constraints registry |
| `outside_subset` | What the contract or the reference implementation supports beyond the subset, with the reason |
| `capabilities` | The capability set, in the vocabulary of `vectors/mission-resource-access/README.md`, that a subset consumer declares |
| `excluded_capabilities` | Capabilities a subset consumer never declares (D414) |

Registry membership and implementation support are separate. All nine initial Common Constraints are in the subset. The reference implementation also supports `terminal_when`, which Discharge registers, and `vendors`, which the payments deployment defines without registering it. Both stay outside the subset, so subset evidence covers Resource Access semantics only.

Input outside the subset is unsupported input: a `prefix` entry, an action family, an entry member outside `members`, and a constraint key outside `constraints`. An authorization server refuses it before approval or transformation and never drops it to manufacture a subset (D152, D538), and a resource server treats an entry carrying it as providing no authority (Resource Access, Resource Server Enforcement). `locations` is refused by name. Since #1377 the reference implementation refuses an action-family value too, before approval or transformation; the sentence in `supported-subset.json`'s `outside_subset.action_families` that says it admits one predates that change, and the file is frozen. Cases ev-fam-01 and der-fam-01 witness a subset consumer's refusal (#819).

The constraint set and the action-family refusal are the owner's ruling (2026-10-22).

## Running the cases under the subset

A consumer declares `capabilities` and runs the files in `vectors/mission-resource-access/` as that README describes: a case runs when the consumer implements every capability in `requires` and none in `unless`. Under the subset that includes the refusals of `prefix` input, which the reference implementation skips because it implements `prefix`.

Input outside the subset appears in a case the subset selects only when the case expects it refused. A case expecting such input handled requires the capability for it (for example `member.delegation` or `resource-match.prefix`), so a subset consumer never runs it. The reference implementation's test checks this for every case the subset selects.

`member.resource_contract` selects the cases about the `resource_contract` member, sub-rc-01 to sub-rc-05: exact preservation of the frozen contract's reference under the subset rule, and a removed, added or substituted reference refused (#819).

Capabilities beyond the subset (delegate matching and eligibility, scope projection, transformation-capability declarations, the `rs.*` resource-server behaviors) are not part of it. A consumer may implement and declare them in addition; its runs of those cases are not subset evidence.

## The second consumer

`src/packages/resource-access-subset-consumer/` is a second consumer of these cases (#819). It declares exactly this fixture's `capabilities`, implements `subset`, `entry-validation`, `resource-match` and `target-resolution` from the Resource Access draft, and runs every case file. It was written against the 152 cases before #1580's additions (71 run, all agreeing); it then ran the 186 cases with no code change: 103 run (53 `subset`, 31 `entry-validation`, 17 `resource-match`, 2 `target-resolution`), all agreeing with the expected outcomes, including the 32 new non-`derive` cases it had not seen, and 83 skipped: 69 for a capability the subset does not declare, 1 inapplicable, and 13 `derive` cases. When #1596 gave `subset` its `refuse` outcome (D727), the consumer was changed to validate both operands before comparing, and to require each operand's `type`; of the 207 cases it then ran 124, all agreeing. When #1595 fixed the currency grammar (D727), it was changed to refuse a malformed `currency`; of the 223 cases it then ran 140, all agreeing. When #1376 stated the `http` and `https` userinfo rule, it was changed to refuse a `resource` carrying userinfo; of the 228 cases it then ran 145, all agreeing. When D858 ruled on A-labels and leap seconds, it was changed to check an `xn--` label's structure and to refuse a Common Constraint date-time value that uses `60` for the seconds field; of the 244 cases it then ran 161, all agreeing. When #249 named the contract's resource (D712, D865), it was changed to refuse a contract reference that the configuration does not name as current for the entry's resource; of the 248 cases it then ran 165, all agreeing. When #1693 published the `payments-runtime-profile-v15` applicability file and cases ev-rc-05 to ev-rc-08 (D889), it ran them with no code change; of the 252 cases it then ran 169, all agreeing. When #813 published the `payments-runtime-profile-v16` applicability file and cases ev-rc-09 to ev-rc-12, it ran them with no code change; of the 256 cases it then ran 173, all agreeing. When #1377 gave `subset` its `enforced_constraints` input (D712), it was changed, by an agent under the same read restrictions, to refuse a key only the candidate carries unless that input names it, checked before the relation; of the 263 cases it then ran 180, all agreeing. When D1025 applied omission-equivalence to both operands, the same author changed it to decide a key's effective presence before that check, so a `requires_action_approval` of `false` neither adds a key nor makes the reference carry one; of the 267 cases it now runs 184 (87 `subset`, 78 `entry-validation`, 17 `resource-match`, 2 `target-resolution`), all agreeing, with the same 83 skipped (69 for a capability the subset does not declare, 1 inapplicable, and 13 `derive` cases).

- **Disagreements.** `test/disagreements.json` is canonical: each entry is a case id, a classification (`case-bug`, `spec-gap`) and the draft text it rests on. The consumer's test fails on an unlisted disagreement and on a listed case that agrees, so the list cannot go stale. It is empty.
- **Scoped out.** `derive` encodes the OAuth binding's derivation as well as Resource Access semantics, so this consumer does not run it, and implements no intersection rule. The checks outside the subset are not implemented.
- **Independence, and its limits.** The consumer imports only Node built-ins and its own modules; its `test/independence.test.ts` fails on any `@mission/*` dependency or on an import leaving the package. It was written in the same repository by the same model family as the reference implementation, under an instruction to read only the Resource Access draft (and the one section of the OAuth binding the draft cites for the digest form), this directory, the case files and their README, and build scaffolding, never the reference's sources or tests; its author's list of every file opened records that it kept to that. That is separate authorship by instruction, not by organization: agreement between the two consumers is evidence that the cases and the draft determine one outcome, not a claim of interoperability between independent implementers.
- **What the cases do not yet exercise**, each tracked separately (D712). These are not all choices the draft leaves open; where the draft or a cited RFC already decides, the gap is in this consumer or in the cases.
  - A-labels: Resource Access requires an A-label as RFC 5890 Section 2.3.2.1 defines it, which is full IDNA2008 validity. The cases fix a structural subset (D858, #1376): the label, read in lower case, decodes under Punycode and encodes back to itself, and the decoded form holds a non-ASCII character, is in NFC and lower case as decoded, does not begin with a combining mark, and meets the hyphen restrictions. This consumer, like the reference implementation, checks that subset and not the RFC 5892 code-point classes, the contextual rules or the Bidi rule, so neither consumer refuses `xn--n3h` (U+2603, which IDNA2008 disallows).
